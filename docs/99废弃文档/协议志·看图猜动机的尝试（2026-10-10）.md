# 协议志 · 看图猜动机的尝试（2026-10-10 ~ 10-11，功能已撤，调用层留给灰色地带）

> 一句话：每 10 秒截一张当前窗口，让决策模型 / 多模态大模型去猜「你此刻在推进哪个动机」——**做得出来、也够快，但方向错了**。
> 截图是一个瞬间，动机需要上下文；看图只能复述屏幕，判断不了价值。代码已全部删掉，这份文档留下过程、数据和想清楚的东西。

---

## 一、当时想做什么

2026-10-10 开始拿自己做一个月的实验（见 `protocol-mode-month`）：每天 10 小时推进 Solevup，进入「AI 操控和感知的智能协议模式」。

那天晚上的设想，以及我（Claude）被授权「放手做」的范围：
- **悬浮的系统窗**：像《我独自升级》的系统面板，浮在桌面右上角，开局 / 心流 / 换事时说一句话。
- **感知内核**：系统得「感同身受」地知道你在推进什么。用决策模型（Jev、Microsoft Decision-1、Liquid d1，走 Vercel AI Gateway）看截图做选择题。
- **今日动机云**：早上立约要推进哪几个动机（理想），一天里感知把时间归到各个动机上（真实），两朵云叠在一起，直接画出「缩短理想与真实的距离」。

## 二、演进过程

| 版本 | 做法 | 用户的反馈 |
|---|---|---|
| v1 | 窗口稳定 3 秒 → 先按标题判大类（编程 / 娱乐…）+ 动机锚点，判不准再截图；同标题缓存，补判今天早些的窗口 | 「活动分类不够细」；想把结果接进昼夜表时被叫停：**昼夜表是给人回忆用的，自动感知灌进去只会是五颜六色的噪音** |
| v2 | 撤掉双轨道和分类，改成每 10 秒截图、不分切没切窗口，猜「当前小目标」；候选 = 动机锚点 + 清单任务 + 这一局用意 + AI 提的小目标；拿不准就在系统窗里问「现在是在……吗？」是 / 不是 / 聊聊 | 「候选小目标还是很慢」「沿用之前判断太过分了，很多时候根本不是选择题，得新建」「出新判断时没弹窗确认」 |
| v3 | 去掉沿用上一帧；选择题后加一道是非题核实（选择题必选一个，核实兜「其实都不是」的底）；更快提假设、更快发问 | 「速度还是好慢……我可以看到思维终端嘛」 |
| v4 | 加「思维终端」：每一步看了什么、挑了谁、核实几分、花了多少毫秒都实时打出来 | **「AI 在这里能做的价值判断非常有限」**——有意义的只有「此刻本应在哪个协议、在不在这个协议里」；而且说好的「动机在空中飘、有亮有暗」的画面还没看到 |
| v5 | 改粗判：只判「在推进云里哪颗动机 / 这一局用意 / 都不在」；动机另开新表（不碰旧锚点，用户要求「纯粹的自嗨式开发，不碰之前的数据库」）；新做今日动机云（推进越久越亮、越靠中心，立约的冰蓝环，此刻那颗敲响共振膜）；一分钟对不上才提议一颗 | 「怎么一分钟都不行」「依旧是一分钟」 |
| v6 | 要「敏感型、快速型、对 token 暴殄天物型」：换窗口停稳 0.6 秒就加看一眼（10 秒只是基础节拍）；一次对不上就提议、提出来直接问；挑选和核实合成一次请求；换窗口时判断和提议并行 | 第二天早上：**「AI 的看图说话其实非常蠢」**，整体撤掉 |

## 三、实测数据（两晚 + 一个早上）

- 决策模型看图判断 371 次（Liquid d1，平均 1.2 秒）＋按标题判断 20 次（Decision-1），合计约 ¥0.31；大模型提议 85 次（千问 Max 3.8，平均 2.8 秒）。钱不是问题，问题是判断本身。
- v6 最终速度：从切窗口到系统窗发问约 3~4 秒（截图 0.14 秒 + 判断 0.7~1.8 秒 + 提议 1.5~2 秒，换窗口时后两者并行）。
- 你一共回答了 26 次：是 22、不是 3、聊聊 1。「是」点得多，不代表猜得对——很多是「大体沾边，懒得纠正」。
- **提议出来的「动机」**（节选，能看出问题在哪）：
  - 前一晚：「搭建游戏饰品自动倒卖套利系统」「搭建 Jev AI 智能体平台」「搭建 Jev AI 语音积分管理平台」「搭建 TypeSafe AI 平台」「搭建 AI 网关监控与成本管理系统」「搭建大模型看图猜题自动套利系统」「搭建赛尔号脱机挂机脚本系统」……
    → 逛一下 Vercel 的模型页就是一个「平台」；看一眼网页标题就是一个「系统」。**每换一个窗口就冒出一颗新动机。**
  - 第二天早上 8 分钟内提了 22 颗：「构建 AI 辅助的本地开发工作流」「构建AI辅助的本地开发工作流」「构建AI自进化本地开发环境」「搭建 AI 自进化本地开发环境」「把 Solevup 做成自进化开发系统」「把协议志做成自进化开发系统」「重构协议志的动静态分工架构」「重构协议志的动静分工架构」「重构协议志的注意力驱动架构」「重构洪流域的注意力驱动架构」……最后一条是「重构洪流域的感知尝试回滚逻辑」——它在读我们讨论撤掉它的对话。
    → 同一件事换个说法就是一颗新动机；点了「不是」，下一句换个词又回来了。
- v2 时期被认过的「小目标」：「在排查Claude Code配额问题」「在调思维终端的TS接口映射」「在修 Rust 后端的结构体反序列化代码」——**准，但只是把屏幕复述了一遍**，用户自己一眼就知道，系统没有多给任何东西。

## 四、为什么不行（想清楚的东西）

1. **截图是一个瞬间，动机是一段上下文。** 同一个 Vercel 页面，可能是在给 Solevup 选模型，也可能是随手逛。图里没有「为什么在这儿」，模型只能就图编一个最像的理由。
2. **看图说话 = 复述屏幕。** 「在调 CSS」「在看 Vercel」是事实，不是判断；把事实包装成「动机」反而失真。
3. **选择题天生偏向「选一个」。** 加了是非题核实也只是压住，压不掉。
4. **否定无法纠正。** 点「不是」只作废那一句；系统没有学到「这一类东西不算」，下一句换个词照样来。
5. **「聊聊」跳进主聊天框，那边的 AI 什么都不知道。** 它没看到系统刚才看到了什么、你之前在做什么，协商无从谈起。
6. **越调越快，错得也越快。** v6 把延迟压到 3~4 秒，换来的是 8 分钟 22 颗重复的动机。速度不是瓶颈，信息才是。
7. 昨天让我放手做，本身就是给自己留思考空间——做出来、跑起来、看到它蠢在哪，比纸上讨论清楚得多。这次尝试的价值在这里。

## 五、正确的分工（第二天想清楚的）

- **Jev / 决策模型只守灰色地带**：问题很简单、选项很少——此刻有没有脱离协议、有没有脱离监控应用的范畴。这是它擅长的（协议白名单锁机 v0 已有，`protocol_gray.rs`）。
- **注意力点用无障碍方式采集**：Windows UI Automation 能直接读焦点控件、编辑器打开的文件、浏览器地址栏和标签页、终端标题、选中的文字——确定的事实，不需要大模型，更不需要 Jev。
- **动机靠上下文 + 人协商**：要和人聊的时候，必须带着之前的注意力轨迹进对话；结论由人给，不由模型猜。
- **主线闭环第一步：AI 监控设备使用**——就这一个功能，先做扎实。

## 六、值得留下的技术发现（以后可直接复用）

- **Vercel AI Gateway 的决策模型接口**（`POST https://ai-gateway.vercel.sh/typesafe/v1/systemone`）：
  - 图片必须放进 `state` 的 content parts：`[{type:"text",text}, {type:"image_url", image_url:{url:"data:image/jpeg;base64,..."}}]`。顶层 `images` 字段会被丢掉；`{type:"image"}` 会把 base64 当文字算 token。
  - 一次请求可以带多道题（一道 choice + 若干 noul），答案按题 id 返回，**只走一趟网络**——比串行两次快一倍。
  - 已提交的灰色地带代码里，看图判断那一路还没按这个格式接，以后接的时候照这个来。
- **千问 Max 3.8（百炼 OpenAI 兼容接口）**一定要 `enable_thinking: false`：开着一句话要 25 秒、上千思考 token，关掉约 2 秒。
- **从 Claude 的 shell 启动应用要先清代理环境变量**，否则应用继承 Clash 代理，国内的百炼会超时。
- **调试版截图慢的真因**：`image` 库的泛型函数（`imageops::resize` 等）在调用方 crate 里实例化，调试版不优化，缩一张整窗截图要 800ms+；只给 `image` 开 `opt-level=3` 不够，要改用 `DynamicImage::thumbnail` / `to_rgb8` 这类非泛型方法（在 `image` 库里编译）。BGRA→RGBA 要原地交换，别逐像素 `extend`。最终截图从 1.5 秒降到 0.14 秒。
- **`BitBlt` 带 `CAPTUREBLT`** 更慢，而且会把悬浮在上面的透明窗（包括我们自己的系统窗）截进去；只截前台窗口时不要带。
- **固定节拍 + 事件加看**：每 0.25 秒瞄一下前台窗口，换了窗口停稳 0.6 秒就加看一眼，两次至少隔 2 秒（防标题一直跳的窗口）。这个节拍结构以后做监控仍然适用。
- **「思维终端」这种可观测性非常值**：一打开就看出慢在截图那一步。以后做任何后台判断，都先让它的每一步可见。

## 七、第二天的实验：把判断模型用在它擅长的地方（10-11）

撤掉之前又玩了一上午，换成问图里**真的有**的东西——「东西在屏幕哪儿」：

| 实验 | 做法 | 结果 |
|---|---|---|
| 图上画格子 + 编号 | 6×4 格画在截图上，选择题「在哪一格」 | 指针 32px；时钟找错（格线遮挡 + 整图缩小后小字糊了） |
| **只发一张干净图，位置写在选项文字里** | 选项用方位词（左上 / 正中 / 右下…）或 0~1000 坐标框；选中后裁出来再问，三轮 | **方位词 6 轮全对**：指针 18px、时钟 11px，三轮约 3.5 秒；坐标框略差 |
| 自适应 5px 定位 | 按长宽比每轮自动切（每向 ≤3 份），选项文字程序生成，切到 ≤5px | 指针最终 **5px**；前 3 轮（到 ~70px）很稳，之后偶尔错到隔壁格（误差被格子大小兜住） |
| 权重光晕 | 每轮的概率一层层乘下去 = 整屏概率分布；权重 ≥0.12 的格都细分（并行）；按「累计概率质量」分层画柔光，不画实线 | 模型越确定光越小越亮（时钟一小团），拿不准就摊开（「注意力在哪」一大片）——如实 |
| 实时分心扫描 | 每 0.4 秒一次，透明鼠标穿透叠加层（`SetWindowDisplayAffinity` 排除截图）上泛红光 | 12 道是非题 → 只会说「这屏是 B 站」，空白处也亮；**多图多题 → 更糟**（对不上哪题对哪图，全屏 0.6~0.8）；**单图选择题 + 「没有」选项 → 对了**：光落在露出来的推荐封面上、终端不亮；`1 −「没有」的概率` = 分心强度 |
| Claude 亲自当判断者 | Claude 认出分心物 + 浓度，程序把框吸附到真实像素（封面按硬边、文字取笔画） | 22 项、像素级，浓度分档合理（人脸大字封面 > 纯文字标题）——「效果简直好多了」 |
| Claude Code 无界面调用（`claude -p`，**必须走 7890 代理**） | 截图 + 主线 + JSON Schema | Opus 5.5：36 秒、19 项，认得全但框偏粗，约 $0.43/次（订阅额度）；Haiku 5.5：45 秒（更慢，多想一轮）、$0.014，漏项认错多 |

结论：
- 决策模型的正确用法：**一张干净图 + 位置写进选项文字的选择题**；是非题容易一律偏高，多图多题会对不上号。
- 它适合「有没有 / 大概在哪」的高频粗扫；「是什么、和主线什么关系」要能看懂内容的大模型。
- Claude Code 当专属 Fairy 的想法（发行版没有）：会话可续 = 有上下文，正好补上这次尝试最缺的东西；但单次 30 秒以上，只适合按需深看，不适合实时。暂缓。
