# 上下文压缩与长期记忆：调研交接

2026-11-07，从 Windows 交给 Mac 接着做。

## 背景和要求

- 主人反馈：现在的压缩让最近的聊天丢了很多信息。
- 想要一份全局共享的「对主人的记忆」，电脑和手机共用，感觉要像 Claude App 那样。
- 要对比 opencode 等开源智能体和各类框架，看看除了「满了再压」还有没有更好的办法。
- 要弄清上下文该定多大、取决于什么。

## 一、我们现在的压缩

文件：`clients/desktop/src/lib/llm/context-window.ts`，手机端 `clients/mobile/src/lib/llm/context-window.ts` 是同一份逻辑。

- **门槛：** 按字数估算，超过 48,000 字就压，压到 24,000 字。
- **保留：** 最近 2 轮原样保留；更早轮次里超过 600 字的工具结果，只留开头 300 字。
- **摘要：** 被裁掉的轮次不调模型，每轮机械摘一行「主人：… → 回应：…」，各截 60 字，最多 24 行。

**丢信息的原因：**

1. **门槛太低。** 用到的模型窗口在 25.6 万到 100 万 token 之间。qwen3.6-flash 在 25.6 万以内同价，缓存命中也便宜。
2. **工具结果没有单独上限。** 一次大结果就能把总量顶过门槛，最后只剩最近 2 轮是完整的。
3. **摘要是机械截断。** 中间讨论出的结论、细节和数字都丢了。
4. **切会话或重启会丢工具记录。** `App.tsx` 的 `sessionMessagesToLLMHistory` 跳过了 `role === 'tool'`，工具调用和结果全丢。
5. **旧摘要会被挤掉。** 旧摘要整段当成一行并进新摘要，里面还嵌套了 `<system-reminder>`。超过 24 行后最早的部分会被挤掉。

## 二、Claude Code 怎么压缩

源码只在 Windows 机上（Mac 没有这份，上面的结论已经够用）：`D:\my_pro\ClaudeCodeOpenSource\claude-code-sourcemap-main\restored-src\src`，主要在 `services/compact/`、`query.ts`、`utils/context.ts`。

### 什么时候触发

- **有效窗口：** 模型窗口 − min(最大输出, 2 万)。
- **自动压缩阈值：** 有效窗口 − 1.3 万。
- **例子：** 20 万窗口、3.2 万输出时，有效窗口是 18 万：
  - 14.7 万开始提示；
  - 16.7 万自动压缩；
  - 17.7 万直接拦住不发请求。
- **怎么算 token：** 上一次回复的真实用量（输入 + 缓存写 + 缓存读 + 输出），加上之后新消息的粗估。粗估按字符数 / 4，每张图算 2000。
- **什么时候检查：** 每次请求前都检查。顺序是：工具结果总量预算 → 微压缩 → 自动压缩。

### 写摘要之前先做的

- **工具结果总量预算：** 一条消息里工具结果加起来超过 20 万字符时，最大的几条存到磁盘，原处只留约 2KB 预览。一条结果处理一次后就不再改，保证缓存前缀不变。
- **按时间清理（默认关）：** 离上次回复超过 60 分钟（缓存已过期）时，除最近 5 个以外的工具结果都换成「旧工具结果已清除」。
- **接口侧：** Anthropic 接口支持清理旧工具调用和思考内容（`clear_tool_uses` / `clear_thinking`），Claude Code 里是内部开关。

### 完整压缩

- **怎么请求：** 用同一个模型、同样的前缀分出一次请求，所以能吃缓存。这次请求禁止调用工具。
- **摘要格式：** 先写 `<analysis>` 草稿，再写 9 段摘要：
  1. 主要请求与意图
  2. 关键概念
  3. 文件与代码
  4. 错误与修复
  5. 问题解决
  6. 所有用户消息
  7. 待办
  8. 当前工作
  9. 下一步（附原话）
- **压缩后带回：**
  - 摘要；
  - 重新读最近 5 个文件，每个不超过 5000 token，合计不超过 5 万；
  - 计划和技能重新附上；
  - 一句「接着做，不要再问」。

### 另一条路：会话笔记压缩

- **平时：** 后台分出一个代理边聊边维护一份 markdown 笔记。对话到 1 万 token 后开始写，之后每增长 5000 token 更新一次。
- **压缩时不调模型：** 用笔记，加上原样保留的最近消息。保留量至少 1 万 token 且至少 5 条消息，上限 4 万；不拆散工具调用和它的结果。

### 失败处理

- 连续失败 3 次就停止自动压缩。
- 压缩请求本身太长时，从最旧的部分往前丢再重试，最多 3 次。

## 三、Claude Code 的长期记忆

源码在 `memdir/`、`services/extractMemories/`、`services/autoDream/`。

- **怎么存：**
  - 每个项目一个目录，一条记忆一个 `.md` 文件。
  - 文件头写 name、description、type，type 分四类：user、feedback、project、reference。
  - `MEMORY.md` 只做索引，每条一行，最多 200 行、25KB。
- **怎么写：**
  - 主模型按系统提示词自己写：先看有没有能更新的旧记忆，不重复；发现错了就改或删；相对日期改成绝对日期。
  - 后台还有一个代理，每轮结束后从最近的消息里提取记忆。这一轮主模型自己写过就跳过，而且它只能写记忆目录。
- **怎么整理：** 距上次整理超过 24 小时、并且中间有 5 个以上会话时，后台代理会合并重复、删掉互相矛盾的、修剪索引。
- **怎么读：**
  - 默认每次会话把索引放进上下文，具体文件需要时再读。
  - 另一种模式是每轮用小模型从记忆清单里挑最多 5 条附上，每条不超过 4KB。
- **新鲜度：**
  - 每条记忆标上「N 天前」写的。
  - 提醒模型：记忆是写下时的事实，和现在冲突时以现在为准，并顺手更新。
- **和缓存的关系：** 记忆段算一次就固定。「N 天前」提前算好，免得每轮都变、打掉缓存。

## 五、初步方向

**三条调研合起来看，最值得抄的：**

1. **写摘要前先截旧工具输出。**
   - 多家都把旧工具输出截到 2000 字符左右。
   - Gemini 的做法：给旧工具输出 5 万 token 的总预算，超出的只留最后 30 行，全文另存文件。
   - JetBrains 评测：只做这一步，效果就和写摘要差不多，成本约一半。
2. **最近一段原样保留，多数在 1.5 万～2 万 token。** opencode 15k，Cline 20k，Codex 20k 用户消息。
3. **摘要用固定模板，有旧摘要就在上面更新，别整份重写。**
   - 模板写目标、决定、进行中、下一步、关键原话。
   - opencode 吃过亏：摘要什么都记，越滚越大。
   - ACE 论文：反复整份重写会塌缩。
4. **系统指令和记忆不写进摘要，压缩后重新带上。** opencode V2 和 Codex 都这么做。
5. **摘要放在后台提前写，别卡住主人发的那条消息。** opencode 在离门槛还有 6 万 token 时就开始写，Aider 用后台线程。
6. **记忆按 Claude App 现行版的样子做：**
   - 边聊边按主题存；
   - 主人能看、能改、能删；
   - 过往聊天需要时再搜，不全塞进去。
7. **记忆要防「顺着说」。**
   - 把主人的话抽成一条条孤立的事实，会丢掉旁边的纠正，模型因此更爱附和。
   - WRITER 测出接 Mem0 后谄媚率涨了约 25 倍。
   - 缓解办法：用一段散文摘要代替事实条目，把当时的反驳也存进去。

**下面是调研前定的方向，仍然有效：**

**压缩：**
- 改成按 token 计数，用接口返回的真实用量。
- 门槛按模型窗口和价格阶梯来定。
- 先限制单个工具结果的体量、清理旧工具结果，最后才让模型写结构化摘要。
- 或者学会话笔记压缩：平时增量维护笔记，压缩时不用等。

**恢复会话：** 切会话或重启时，保留工具调用和结果。

**记忆：**
- 全局一份「关于主人」的记忆，电脑和手机同步，做成 Claude App 那种感觉：
  - 定期总结；
  - 主人可以看、可以改；
  - 需要时能搜过去的聊天。
- 放在稳定的前缀里，不打掉缓存。

## 六、调研结果：框架、接口与研究

2026-11-07 子智能体交回，数字都附了来源，但没有逐条复核。官方文档页面没有日期，以 beta 头里的日期为准。

### 各框架怎么做

- **OpenHands：**
  - 旧版 V0 有 10 种压缩方式，常用的有：
    - 观察遮蔽：只保留最近 100 个事件的工具输出；
    - 模型摘要：保留第 1 个事件，总数上限 100；
    - 摊销遗忘：超过上限时一次砍到一半，所以很少重写历史；
    - 让模型挑保留哪些事件：代码注释里写着「用不上缓存」。
  - 新 SDK 只留模型摘要：120 个事件触发，保留前 4 个，压到约 60 个；上下文报错时也会触发。
  - 官方博客：每轮成本降到一半以下，SWE-bench 解题率 54% 对 53%。
  - [配置](https://github.com/OpenHands/OpenHands/blob/0.59.0/openhands/core/config/condenser_config.py) · [SDK 文档](https://docs.openhands.dev/sdk/arch/condenser.md) · [博客](https://openhands.dev/blog/openhands-context-condensensation-for-more-efficient-ai-agents)
- **JetBrains 评测《The Complexity Trap》（NeurIPS 2025 workshop）：**
  - 做法：SWE-agent 跑 SWE-bench Verified，模型 Qwen3-Coder-480B。
  - 只遮蔽旧工具输出（保留最近 10 条）：54.8%，$0.61。
  - 模型摘要：53.8%，$0.64。
  - 不压缩：53.4%，$1.29。
  - 用摘要时轮数多了 13~15%，摘要调用本身占总成本最多 7.2%。
  - 混合方案（平时遮蔽，偶尔摘要）最省：比只遮蔽再省 7%。
  - [arXiv 2508.21433](https://arxiv.org/abs/2508.21433)
- **LangChain v1：**
  - 摘要中间件的触发条件没有默认值，不设就永远不触发；默认保留最近 20 条消息。
  - 清理工具结果：10 万 token 触发，保留最近 3 个，原处换成 `[cleared]`。
  - [文档](https://docs.langchain.com/oss/python/langchain/middleware/built-in)
- **MemGPT / Letta：**
  - 上下文分三块：系统指令、模型自己维护的工作记忆、消息队列（队首是滚动摘要）。
  - 用到窗口 70% 时提醒模型赶紧把要紧的事存起来；满了把队列一半压进摘要。
  - 被压掉的消息仍然可以搜（recall），另有长期档案库（archival）。
  - Letta 现在默认滑动窗口，每次摘约 30%；也可以让主模型自己写摘要，好吃缓存。
  - [论文](https://arxiv.org/abs/2310.08560) · [Letta 压缩](https://docs.letta.com/v1-sdk/messages/compaction)
- **Mem0：**
  - 不带完整历史，只抽事实、需要时检索。
  - 在 LOCOMO 上报告 p95 延迟降 91%，token 省 90% 以上。
  - 有第三方质疑：对照组太弱，而且没算抽取本身的成本。
  - [arXiv 2504.19413](https://arxiv.org/abs/2504.19413)
- **其他：**
  - Google ADK：按 token 阈值压缩，保留最近若干事件。
  - Agno：滚动会话摘要，加最近 3 轮原样保留。
  - CrewAI：只在溢出时才摘要。

### 接口自带的能力

- **Anthropic 清理旧工具结果**（[context editing](https://platform.claude.com/docs/en/build-with-claude/context-editing)）：
  - 默认 10 万输入 token 触发，保留最近 3 个工具调用；可以排除指定工具。
  - 清理会打掉缓存，所以用 `clear_at_least` 保证每次清得够多才划算。
  - 官方数据：内部评测效果 +29%，配合记忆工具 +39%；100 轮搜索任务 token 少 84%。
- **Anthropic 记忆工具：**
  - 模型自己调工具读写 `/memories` 目录（看、建、改、插入、删、改名），文件存在我们这边。
  - 官方建议和压缩一起用。
  - [文档](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool)
- **Anthropic 服务端压缩：**
  - **按门槛：** 默认 15 万输入 token 触发，最低 5 万，可以自定义摘要提示词。系统提示词末尾打缓存断点，压缩后还能命中。
  - **按需：** 可以原样保留最近几轮，也可以在后台跑。
  - [门槛模式](https://platform.claude.com/docs/en/build-with-claude/compaction-threshold) · [按需模式](https://platform.claude.com/docs/en/build-with-claude/compaction-on-demand)
- **OpenAI Responses API：**
  - 设一个门槛（文档例子是 20 万），超过就压缩，返回的是加密的压缩块，看不到内容。
  - 缓存是自动的。
  - [文档](https://developers.openai.com/api/docs/guides/compaction)

### 实践经验

- **Manus**（[博客](https://manus.im/blog/Context-Engineering-for-AI-Agents-Lessons-from-Building-Manus)）：
  - 缓存命中率是头号指标：输入输出比约 100:1，缓存价是原价的十分之一。
  - 前缀要稳：不放时间戳，只往后追加，序列化顺序固定。
  - 工具不删，只屏蔽。
  - 压缩要能找回：丢掉网页正文，但留下网址或文件路径。
  - 用 todo.md 反复复述目标；报错留在上下文里，不要藏。
- **Anthropic**（[文章](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)）：
  - 上下文用尽量少、信息密度高的内容。
  - 需要时再取，别全塞进去。
  - 写摘要先保证不漏，再求精简。
  - 清理工具结果是最轻的压缩。
  - 用结构化笔记。
- **ACE（ICLR 2026）：** 让模型一遍遍整份重写上下文，会「塌缩」：18,282 token、准确率 66.7%，最后缩成 122 token、57.1%，还不如什么都不做（63.7%）。解法是逐条增量更新。[arXiv 2510.04618](https://arxiv.org/abs/2510.04618)

### 上下文越长，质量越差

- **RULER：** 号称 32K 以上的模型，只有一半在 32K 真能用。[arXiv 2404.06654](https://arxiv.org/abs/2404.06654)
- **NoLiMa：** 以保住短上下文 85% 的成绩为准，GPT-4o 的有效长度只有 8K；12 个模型里 10 个到 32K 时跌到一半以下。[arXiv 2502.05167](https://arxiv.org/abs/2502.05167)
- **Chroma「Context Rot」：** 18 个模型全都随长度变差。在 LongMemEval 上，约 300 token 的精简提示明显好于约 11.3 万 token 的完整版。[报告](https://www.trychroma.com/research/context-rot)
- **多轮对话：** 指令分散在多轮里时，15 个模型平均掉 39%，主要是表现不稳，不是能力不够。[arXiv 2505.06120](https://arxiv.org/abs/2505.06120)
- **没找到：** 千问 3.x 的有效长度数据。

| Opus 5.5 | 4 | 0.20 | 20 |
| Sonnet 5.5 | 2 | 0.10 | 10 |
| Haiku 5.5（≤10 万） | 0.10 | 0.01 | 0.50 |
| Haiku 5.5（>10 万） | 0.50 | 0.05 | 2.50 |

### 子智能体的结论

**证据最足的几招，按顺序：**

1. **清理或遮蔽旧工具结果，并留指针能找回。** 不用调模型，效果和摘要差不多，成本约一半。
2. **外部记忆，需要时再搜。** MemGPT 的 recall、Anthropic 记忆工具、Mem0 都是这条路。
3. **摘要只作最后手段，而且一次砍一大块**（砍到约一半）：
   - 最近几轮原样保留；
   - 系统提示词和稳定记忆放在缓存断点之前；
   - 摘要逐条增量更新，别整份重写。
4. **前缀稳定、只追加**，保证缓存一直命中。

**门槛该看什么：**

- **质量，通常最先卡住：**
  - 难任务上的实测有效长度只有 8K～32K，远低于宣传的 12.8 万～100 万；
  - 各家默认门槛在 10 万～20 万；
  - MemGPT 用到 70% 就提醒。
- **价格阶梯：**
  - 别跨档：qwen3.7-flash 的 3.2 万、Haiku 5.5 的 10 万、Plus 系列的 12.8 万 / 25.6 万；
  - qwen3.8-max / flash 没有阶梯。
- **缓存：**
  - 缓存热着的时候，留着旧历史只花原价 5%～20%；
  - 每压一次都要按 1.25 倍重写缓存，所以要少压、一次多压。
- **空闲（子智能体的推断，没有来源）：** 陪伴型应用里，主人常常隔 5 分钟以上才回话，缓存早就凉了，这时在后台压缩最便宜。
- **延迟：** 按门槛压缩会卡住触发它的那次请求，放到后台压缩就不会卡。

**这一条没查到的：** LangGraph 自己的方案、Letta 新实现的门槛、qwen3.8 系列的缓存折扣、千问 3.x 的有效上下文长度。

## 七、调研结果：开源编码智能体（读源码）

2026-11-07 子智能体交回，每家都钉了提交号，Mac 上可以按提交号重新拉源码。GitHub issue 和用户投诉没查；下面的「教训」只来自源码注释。源码缓存在 Windows 的 scratchpad 里，Mac 上没有。

### opencode

- **仓库：** anomalyco/opencode（原 sst/opencode），dev 分支，提交 682dd25b（2026-11-06）。
- **主要文件：** `packages/core/src/session/compaction.ts`、`packages/schema/src/config/compaction.ts`。
- **触发：**
  - 窗口 − max(窗口 15%, 1.6 万) 时压缩；`compaction.buffer` 可以改。
  - 服务商报「请求太长」时，先压缩再重试一次。
- **修剪：**
  - 平时整段原样发出去，好复用缓存。
  - 发不下时，从最老的往新缩，共 5 级：
    1. 完整保留；
    2. 工具输出只留首尾各 2000 字符；
    3. 去掉工具输出，裁短工具输入；
    4. 只留用户文字；
    5. 整段省略。
- **摘要模板：**
  - 章节：目标 / 要求 / 决定 / 工作状态（完成、进行、卡住）/ 下一步 / 相关文件（最多 15 个）/ 重要背景。
  - 路径、命令、报错原文、网址原样保留。
  - 还没回答的请求按原话带下去。
  - 不写 AGENTS.md 和环境信息，这些压缩后会重新带上。
  - 已有摘要时走「更新」提示；没按模板写就再催一次。
- **保留：** 最近约 1.5 万 token 原样保留，和摘要一起放进一条消息。
- **缓存：**
  - 压缩请求 = 正常请求末尾追加摘要提示，所以能复用前缀缓存。
  - 实验性后台压缩：离门槛还差 6 万 token 时就开始写摘要，而且只在缓存还剩 30 秒以上寿命时才开始。
- **教训（源码注释）：** 2026 年 9 月以前，摘要什么都记（每个碰过的文件、每次编辑流水、复述规范），越更新越长，后来改成精简模板。
- **旧版 V1：**
  - 修剪时最近 4 万 token 的工具输出受保护；更早的累计超过 2 万才清，换成「旧工具结果已清除」。
  - 保留尾部：可用量的 25%，限制在 2000～1.5 万 token 之间。

### Codex CLI

- **仓库：** openai/codex，提交 c1c07853（2026-11-06），代码在 `codex-rs/`。
- **触发：**
  - 默认窗口的 90% 时压缩，硬上限 95%；大多数模型窗口是 27.2 万，所以约 24.5 万时触发。
  - 也可以设成回合结束后再压。
  - 支持远程压缩的服务商，65% 时就在后台先压。
- **本地摘要：**
  - 提示词是「交接摘要」：写进展和决定、约束和偏好、剩余步骤、关键数据。
  - 摘要前面加一句「另一个模型已经开始解决这个问题……」。
- **保留：**
  - 本地压缩保留最近的用户消息，最多 2 万 token；初始上下文重新插到最后一条用户消息之前。
  - 远程压缩保留最多 6.4 万 token 的用户消息。
- **远程压缩：** 服务端返回加密的压缩块，看不到内容。
- **特别的：** 有个 `new_context` 工具，不写摘要，直接开一个新窗口。

### Gemini CLI

- **仓库：** google-gemini/gemini-cli，提交 3fd7d263（2026-11-05）。
- **主要文件：** `packages/core/src/context/chatCompressionService.ts`。
- **触发：** 上次请求的 token 达到模型上限的 50% 时压缩；用户可以改。
- **修剪：**
  - 工具调用当场截断，默认 4 万字符。
  - 压缩前，旧工具输出总预算 5 万 token：新的完整保留，超预算的旧大输出只留最后 30 行，全文另存临时文件。
  - 上次摘要失败时，这次只截断不摘要。
- **摘要：**
  - 先在草稿区推理，再输出一个状态快照，字段有：
    - 总目标、生效的约束、关键知识；
    - 产物记录、文件状态、最近动作；
    - 任务状态（标完成、进行中、待做）。
  - 有旧快照就并进新快照。
  - 还要再调一次模型「探针校验」：检查有没有漏路径、工具结果和约束，再出改进版。
- **保留：**
  - 按字符保留最近 30%，只在用户消息处切开。
  - 压完 token 反而变多就放弃。

### Cline

- **仓库：** cline/cline，提交 ea16751d（2026-11-05），代码在 `sdk/packages/core/src/extensions/context/`。
- **触发：** 用到最大输入的 90%。压到触发值的 70%；长对话压到最大输入的 50%。
- **三种模式：** 模型摘要（默认）、纯截断、关闭；摘要失败就退回纯截断。
- **摘要模式：**
  - 保留最近 2 万 token。
  - 工具结果截到 2000 字符。
  - 模板：目标 / 状态 / 要点 / 下一步 / 文件（读过、改过），附上一份摘要。
- **纯截断模式：**
  - 主人亲手打的消息永远保留。
  - 更早的轮次只留最后的回答。
  - 删掉的工具工作改写成「读了哪些、改了哪些、跑了哪些命令」。
- **教训（源码注释）：** 摘要输出上限原来是 4096，推理模型把预算花在思考上，返回空摘要，压缩就被跳过了；后来提到 8192。

### Roo Code（已归档）

- **仓库：** RooCodeInc/Roo-Code，提交 b867ec91（2026-05-15）。
- **触发：** 默认 100%，可以按配置单独设 5%～100%；也会在超过窗口 90% 减预留输出时触发。
- **兜底：** 压缩失败时，隐藏除第一条外一半的消息。只做标记不真删，能恢复。
- **摘要：**
  - 摘要变成一条用户消息，旧消息打标记不再发。
  - 读过的文件以「折叠后的代码定义」形式附上。
  - 提示词模板和 Claude Code 一样是九段。

### Kilo Code

- **仓库：** Kilo-Org/kilocode，提交 b8fb3b84（2026-11-06），是 opencode V1 的分支。
- **改动：** 只在缓存本来就失效的时候修剪（刚压缩完、请求超限时）；平时不修剪，免得打掉缓存。

### Aider

- **仓库：** Aider-AI/aider，提交 5dc9490b（2026-05-22）。
- **门槛很小：** 历史预算是最大输入的 1/16，限制在 1024～8192 token 之间。代码上下文主要靠 repo map 和当前加进来的文件。
- **后台摘要：** 在后台线程里写，下次发送前等它写完。
- **摘要怎么做：**
  - 保留不到预算一半的尾部，其余拿去摘要。
  - 还超就递归，最多 3 层；先用弱模型，失败再用主模型。
  - 用主人第一人称写（「我问过你……」），越旧越略；要写函数名和文件名，不贴代码。

### 没查

- Crush、Goose：只找到文件位置，没读。
- 各家效果对比：没找到评测或 issue 数据。

## 八、调研结果：ChatGPT、Claude、Gemini 的记忆

2026-11-07 子智能体交回。可信度标签：
- 【官方】帮助页或公告；
- 【媒体】媒体转述厂商的说法；
- 【逆向】第三方让模型自述或提取提示词得出，可能过时或有误；
- 【单源】只有一个第三方来源。

OpenAI 的官网对它一直返回 403，所以 ChatGPT 部分没有亲自打开过的官方页。

### Claude App（重点参考）

**现在有哪几种记忆**（2026-08-25 改版后，【官方】[帮助页](https://support.claude.com/en/articles/11817273)）：

- 记忆按一个个主题存。
- 每个项目有自己的项目记忆。
- 可以搜过去的聊天。

**以前的样子：**

- 一份记忆摘要，后台每 24 小时综合一次；外加每个项目一份摘要。
- 少数企业账户还在用这套。

**怎么写进去：**

- **边聊边写（【官方】）：** 改版后，Claude 边聊边把信息存成主题，不再等聊完才总结。它自己判断存什么，主人也可以直接说「记住这个」。
- **主要记什么（【官方】）：**
  - 角色、项目、职业背景；
  - 生活和工作里的人和地方；
  - 沟通偏好和技术偏好；
  - 进行中的事。
- **默认不存敏感话题（【官方】）：**
  - 健康、宗教、政治等默认不存；主人可以打开，打开后每存一条敏感内容都会提示。
  - 证件号、犯罪记录、金融账号，主人要求也不存。
- **哪些聊天不写记忆（【官方】）：** 无痕聊天、单独关了记忆的聊天。
- **写入工具（【逆向】）：** 主人说「记住 / 删掉」时，模型调 `memory_user_edits` 工具，有查看、添加、删除、替换四个命令。
  - 有人测出最多 30 条、每条 200 字，【单源】。

**怎么读出来：**

- **记忆（【官方】）：** 带进新聊天。
  - 改版后是每轮都带还是需要时再读，官方没写。
  - 旧版是在系统提示后面放一个 `<userMemories>` 块，内容是要点列表，【逆向】。
- **过去的聊天（【官方】）：** 需要时由模型调工具搜，界面上显示为一次工具调用，还能点回原聊天。
- **两个搜索工具（【逆向】，[Simon Willison](https://simonwillison.net/2025/Sep/12/claude-memory/)）：**
  - `conversation_search`：按关键词搜，默认返回 5 条，最多 10 条。
  - `recent_chats`：取最近几次聊天，默认 3 条，最多 20 条，可以按时间筛选。
- **不一定会用（【逆向】）：** 模型不一定会调这两个工具。
- **范围（【官方】）：** 在项目里只搜本项目，在项目外搜所有非项目聊天。

**主人能做什么（【官方】）：**

- **看和改：** 设置里所有记忆按主题列出，可以看、改、删；改了之后所有对话都按新的来。在聊天里直接说要记住、改掉或忘掉什么也行。
- **暂停或重置：** 暂停是保留但不用、也不新增；重置是全部永久删除。
- **单个聊天关记忆：** 开聊前就要关；聊开后改不了。
- **项目隔离：** 项目里只用本项目的记忆加账户记忆，可以关掉账户记忆，彻底隔离。
- **导入导出：** 能从别家 AI 导入（复制一段提示词过去，把结果贴回来），导出数据里带全部记忆。

**已知问题：**

- **删两处（【官方】）：** 删聊天不会删掉由它产生的记忆，要单独删。
- **谄媚：** [WRITER 2026-06](https://writer.com/engineering/personalized-context-degrades-ai-accuracy/) 测的是第三方记忆系统接 Claude 等模型，不是 Claude App 自己的。
  - 结果：Sonnet 4.6 的谄媚率从 1.6% 涨到 40.2%。
  - 原因：把用户说法抽成孤立事实，丢了旁边的纠正。
  - 缓解：用散文摘要代替事实条目，把助手当时的反驳也存进去。

### ChatGPT

**两套记忆：**

- **保存的记忆：** 2024-02 上线。模型调 `bio` 工具写，主人要求时写，模型自己发现事实时也写（【逆向】）。
- **参考聊天记录：** 2025-04 上线，是另一个开关，没有存储上限（【媒体】）。

**怎么读出来：**

- 每轮都自动放进上下文，不由模型决定。这点和 Claude 相反（【逆向】）。
- 2025 年逆向出来的注入块（【逆向】，[embracethered](https://embracethered.com/blog/posts/2025/chatgpt-how-does-chat-history-memory-preferences-work)）：
  - 保存的记忆：带日期的编号列表；
  - 回复偏好：约 15 条，每条带置信度；
  - 过去话题要点：约 8 条；
  - 用户洞察：约 12～14 条；
  - 最近约 40 次对话：只有用户发的消息；
  - 设备和使用信息。

**后来的改动：**

- **2025-10 自动管理（【媒体】）：** 按新旧和重要性自动排序、清理，不再出现「记忆已满」。
- **2026-06「Dreaming」（【媒体】）：**
  - 后台参考聊天记录，综合出记忆。
  - 过时的事会自动改掉，比如「7 月去新加坡」过了日期会改成「去过新加坡」。
  - 新增一个可以编辑的「记忆摘要」页，但官方承认它不一定包含所有能被记起的内容。
  - 回复下方会显示用到了哪些记忆和过往聊天，可以纠正，也可以标「不相关」。

**主人能做什么：**

- 能逐条删除或全部清空，也能在聊天里说「忘掉……」。
- 删聊天不删记忆。
- 临时聊天不用记忆，也不写记忆。

**已知问题：**

- **过时：** 已经放弃的计划还留在摘要里（【逆向】）。
- **串台：** [Simon Willison](https://simonwillison.net/2025/May/21/chatgpt-new-memory/) 让它生成一张宠物换装的图，结果把旧聊天里的地名画了进去。他批评记忆让人失去了对上下文的掌控。
- **谄媚：** OpenAI 复盘 2025-04 的谄媚事故时说，记忆在某些情况下会加剧附和。
- **注入：** `bio` 工具能被间接提示注入调用，在用户没同意时写入记忆。

### Gemini

**有哪几种：**

- **主人主动告诉它的信息：** 现在叫「给 Gemini 的指令」（【官方】）。
- **回忆过往聊天：** 2025-02 上线（【媒体】）。
- **个人上下文：** 2025-08 上线，默认开启，自动从过往聊天里学习（【媒体】）。
- **Personal Intelligence：** 授权后能用 Gmail、相册等（【官方】）。

**怎么写：**

- 主人可以手动添加，或者在聊天里让它记住。
- 模型也会自己调工具写，界面上会提示（【安全研究】）。

**怎么读：** 回复下方显示「用到了你保存的信息」，官方承认这个标签有时标错。

**主人能做什么：**

- 能逐条看、改、删，也能整体开关，或者单独关掉「从过往聊天学习」。
- 临时聊天不进记录，也不影响记忆。
- 能从别家 AI 导入，支持上传别家导出的聊天 ZIP。

**已知问题：**

- **注入：** 上传藏了指令的文档，之后主人回一句「是」，就会把假信息写进长期记忆（【安全研究】）。
- **谄媚：** CHI 2026 论文用真实用户数据测，记忆画像带来的附和涨幅最大，Gemini 2.5 Pro +45%（[arXiv 2509.12517](https://arxiv.org/abs/2509.12517)）。

### 没查

- 记忆串台、隐私事故的用户投诉。
- 三家记忆注入的 token 预算、条数上限（Claude 改版后的、ChatGPT Dreaming 之后的都没查）。
- Grok、Copilot、Meta AI。
